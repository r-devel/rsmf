### Sovereign Tech Fund Milestone 8: Portability and Maintainability

***********************************************************************

Milestone 8: Improve portability and maintainability of R across hardware
platforms, including toolchains, new deadline 31 December 2026

This milestone is reached when a plan is developed which enables abstracting
the building process, away from assumptions about specific runtime platforms
including hard coded solutions, their architectural hardware components (e. 
g.  CPU architecture) and their associated compiler specifity in order to
enable portability and maintainability despite for variations and changes
due to fast developments in the technology.  This milestone is considered
complete after researching the necessary changes for portability, and
developing an associated tool-chain (compiler +libraries) is performed such
that both R and its packages can be seamlessly built on various systems when
being tested against specific hardware architectures using LLVM/arm64
support as its target test case.

***********************************************************************

    - is hasNoNameSpaceError relevant anymore?
    - curl_error is used one time in tools package. Covers sending and receiving but could distinguish.
    - packageConflictError is here because you're attempting to load a package, and it is throwing an error
    - packageError is anything that caused the package to not successfully load.
         - possibly should be separate branch as may not be due to I/O error

    - typeError is you gave the wrong type of thing entirely.
    - typeMismatchError: two arguments need to have the same type, and they don't
    - multiMissingArgsError: these can't all not be set at the same time.
     
 - Everything else is sort of miscellaneous stuff, like there's parse error that will just probably sit by itself as a parse error

### Deprecation scaffolding (https://github.com/r-devel/r-project-sprint-2026/issues/18) [01:47:24]

 - Idea to have some mechanism for tracking deprecation
 - Primary motivation is for base R, but Martin Maechler mentioned it could be good to have something that also applies to packages
 - Proposal is to add some structured data to the NEWS file entries
     - Still human-readable
     - Can be extracted from NEWS file for tracking/summarisation
 - Proposed specification:
     ```
     Deprecation|Defunct|Removal:Free text msg; scope; [proposed deprecation duration; proposed defunct duration]
     ```
     - prefix declaring status
     - free text message as in current NEWS items
     - scope: one of fixed set, e.g. `rfun` - Full R function; `rarg` - Argument deprecation, etc
     - optional durations at end, in x.y format (x is number of major releases and y is number of minor, non-patch releases)
     
  - Rather than modifying old NEWS files, would go back and collate past deprecations in separate file
  - Sebastian: Maybe better to use Rd macro, so can store information in Rd file, but not affect rendered news?
      - Not so convenient for packages that mostly use NEWS.md vs NEWS.Rd
  - For R-level deprecations, can detect with .Deprecated function, can't detect C-level deprecations, where deprecation is telling people not to use it and removal is removing from API.
  - Tooling based on NEWS entries: if no duration, can just show time since the function was deprecated, as a reminder before release
  - Historically, not all the deprecations have been put in the Deprecated or Defunct sections of the NEWS, especially C-level ones
  - Quite a bit of duplication: the deprecated and defunct help pages (e.g. base-deprecated); NEWS, Rd comments    
      - Having scope in specification would enable determining if something needs to go on deprecated or defunct help page
  - Mikael: Would be good to have metadata in deprecated warning. E.g. for Matrix, would like to do reverse dependency checks and promote just those warnings to errors, and then I know exactly which are using my deprecated stuff.
  - Mikael: Rather than use NEWS, which can have different formats, could use database that has to be stored in a certain location
      - Gabe: true, but news() function knows how to read all the formats
      - Heather: encouraging maintainers to put deprecations in the NEWS file could be a good thing
  - Some discussion on how "human-readable" the specification is:
      - Sebastian: not sure he'd like to see metadata (e.g. scope) in NEWS file - better in .md or .Rd comment
      - Gabe: then NEWS wouldn't be supported
      - Thomas: having "Deprecation:" at beginning is not a disadvantage
      - Gabe: not all deprecations were in Deprecation section, sometimes need to read full news item to work out its a deprecation
      - Heather: maybe could be made more human readable, e.g. "Deprecation (rfun): free text"
      - Sebastian: Current specification does not name function in metadata
  - Tooling could
     - Highlight functions that should be made defunct in upcoming release
     - Check if there are news entries for deprecated R functions
  - Can at least decide on something that would work for base R and recommended packages
     - Could possibly propose that lifecycle package also updates NEWS file in proposed way, if compatible
  - For base R, non-patch releases are equivalent to years - not true for R packages, even recommended ones
     - Many users update annually rather than with every release
     - Specifying durations in years would give a minimum time users can count on old behaviour
  - Could consider defined/default cadence, e.g. similar to Python
     - Could scrape Rd comments to see typical cadence in base R
     - E.g. codify making defunct if been deprecated x years since major release

### Untranslating error messages: https://github.com/r-devel/r-project-sprint-2026/issues/19
    
- During the sprint, Ivan Krylov considered 3 possible ways to implement this, but all of them 
are bad
- Discussion of these options in this meeting lead to a new idea, linking to Gabe's work on classed 
errors.
- If we have classed errors, even error/condition objects from the C level, we could do `format(<cond.object>)` , with 

    ```r
    format.translatableError <- function(object, translate = TRUE, ...){
         if (translate) {
             do.call(gettextf, c(list(object$fmt), object$args, list(domain = object$domain)))
        } else {
             do.call(sprintf, c(list(object$fmt), object$args))
        }
    }
    ```
    
    This won't magically make all the errors that we already have un-translatable, but a sufficiently convenient API will hopefully convince package developers to use it instead of the old ways
